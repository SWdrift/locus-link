# Locus Link 声明与解析设计

## 简述

本文定义从声明组织到 Resolve 结果的同一份技术契约：Registry 组织声明，Scope 与 canonical identity 赋予对象稳定身份，静态校验建立可解释的 declared view，Runtime Context 决定显式 Route 在本次调用中是否适用，Resolve 再组合 Provider 原生上下文、文档引用和已有证据。

Registry 只是 Declaration 的存储与组织机制，不是产品本体。Entity、Link、Route 的产品含义和信息归属由[产品设计](产品设计.md)定义；命令、参数、输出和退出码由[CLI 设计](CLI设计.md)定义；当前目录布局、字段覆盖和实现范围见[当前实现快照](../current-architecture.md)。

## 职责

本文负责：

- 定义 Scope、Import、Binding、namespace、canonical identity 与 additive composition；
- 定义声明引用、Provider data 和 documentation reference 的技术约束；
- 划分静态有效、运行时适用和现实证据三个判断层；
- 定义 Runtime Context、target resolution、显式 Route 匹配与候选基数；
- 定义 resolved result 的组成和 Resolve 的只读边界。

本文不负责：

- 重复定义 Entity、Link、Route 的产品语义或信息生命周期；
- 定义 CLI 的发现参数、展示格式和用户可见错误；
- 自动发现、搜索或执行未声明路径；
- 用 Registry、Observation 或 Provider 构造另一套产品本体。

## 三层判断

```text
静态有效：声明本身是否自洽
    ↓
运行时适用：显式 Route 是否适合本次 Runtime Context
    ↓
现实证据：最近实际测量支持到什么程度
```

三层不可互相替代：

- 静态有效不表示当前机器、网络位置或工具能够使用该 Route；
- 运行时适用不表示 Route 已被探测成功；
- success、failure、stale 或 unknown evidence 都不修改声明，也不决定 Route 是否成为候选；
- Resolve 必须分别暴露匹配结果和 evidence，不能把二者压成一个“可用”布尔值。

## 声明组织

### Scope、Import 与组合

每份声明属于一个具有稳定 `scope.id` 的 Scope。Scope kind 为 `project` 或 `environment`；Project 可以通过唯一 alias 导入 Environment。Import path 如何定位 Registry 属于当前实现事实，导入后的语义固定为：

```text
Project declarations
+ imported Environment declarations
→ composed declared view
```

组合只做引用归一化和集合并集，不做 overlay、字段 merge、override 或 precedence。导入声明在 Project 的 composed view 中保持原身份；需要表达不同事实时，应声明新对象或让 Binding 指向其他 Entity。

同一 composed view 中，重复 Scope ID、重复 import alias 和 import cycle 均无效。Environment 作为 active Scope 时没有 Project Binding。

### Canonical identity 与引用

声明文件使用 Scope 内 local ID；加载后统一形成：

```text
<scope-id>::<local-id>
```

`::` 保留给 canonical identity，import alias 不进入 canonical ID。local ID 在所属 Scope 的全部声明对象类型中唯一；不同 Scope 可以使用相同 local ID。Scope ID、local ID、alias 与 Binding role 只使用小写字母、数字、`.`、`_`、`-`。

引用规则：

- canonical ID 可以直接引用对象；
- alias-qualified ID 指向已导入 Scope，加载后立即归一化为 canonical ID；
- 裸 local ID 只在 active Scope 中解析，不从多个 imported Scope 猜测；
- Link 的 `from`、`to` 必须归一化为 Entity；Route step 必须归一化为 Link；
- CLI 对象身份和 Observation subject 使用 canonical ID。

### Binding

Binding 只表达：

```text
Project role → canonical Entity
```

Binding 不是 Entity、Link 或 Route，不表示 reachability、不提供 capability，也不携带条件、优先级或多候选。目标可以是 Project-local 或 imported Entity。解析后必须同时保留输入 role 与 canonical target，避免无痕解引用。

### 声明与关联资料

声明使用带 API version 和明确类型的严格结构；核心字段使用 `snake_case`，未知核心字段无效，Provider 专属字段由对应 Provider 校验。每个声明输入只承载一个文档对象。当前序列化格式与字段清单见[当前实现快照](../current-architecture.md)，不由本文把某一版实现永久化。

技术关系保持以下约束：

- Link 引用明确的 `from`、`to` 和 Provider，并以开放字符串表达 `requires` / `provides`；
- Route 只编排 ordered Link steps；target 从最后一个 Link 的 `to` 推导，capability 由 ordered Links 的 capability fold 推导；
- 每一步的 `requires` 必须由前序累计 `provides` 满足；Route 不要求 `previous.to == next.from`；
- 不自动组合 Link、不做图搜索，也不以声明顺序补充隐藏语义；
- Secret 只保存 credential reference 或外部配置 reference，不保存 Secret value。

Entity、Link、Route 可以关联 documentation references。引用相对声明来源归一化，并保留 canonical subject、ref 和可选 title。文档内容不覆盖结构化字段，不参与 capability fold、Route applicability、Provider 渲染或执行；Resolve 只发现和返回引用，不解释正文。

## 静态校验

静态校验在任何 Route 匹配前完成，并且只回答 declared view 是否自洽：

- API version、严格字段、Scope / Import / Binding 结构合法；
- identity 唯一，引用存在且类型正确；
- alias-qualified 和跨 Scope 引用可唯一归一化；
- Route 的 ordered capability fold 成立；
- Provider 已注册，Provider data 通过其 `Validate`；
- documentation reference 指向可发现的文档资源；Markdown anchor 不参与结构校验。

静态校验不连接 endpoint、不读取 Observation、不要求 current Entity 或 vantage，也不探测 Provider executable。校验规则只有这一处；Resolve 消费已经校验和 canonicalized 的 declared view，不维护第二套 identity、引用或 capability fold 逻辑。

## Runtime Context

Runtime Context 是一次 Resolve / Probe 调用的现场输入，不是可以任意扩张的 session model。它至少提供：

- active declared view；
- `current_entity`：本次调用的 operational actor；
- `vantage`：选择适用 Observation 的观察位置；
- Provider 渲染或后续实例化明确需要、且不属于 Declaration 的调用时上下文。

`current_entity` 与 `vantage` 含义不同，不能互相推导。Secret value、临时 tunnel port、token、SQL、session 和 Provider 运行资源属于未来 Instance 或外部机制，不回写 Declaration。Runtime Context 的当前采集方式、fallback 和字段覆盖见[当前实现快照](../current-architecture.md)。

## Target resolution

输入 target 按以下顺序解析：

1. active Project 的 Binding role；
2. canonical Entity ID；
3. import alias-qualified Entity ID；
4. active Scope local Entity ID。

结果必须是 canonical Entity。不得从 imported Scope 猜测裸 local ID，也不得以 Route、Link 或 capability 代替 target。Binding 命中时，结果同时保留输入 role 和 canonical target。

## Route applicability

Resolve 只匹配 composed declared view 中显式声明且已通过静态校验的 Route。候选必须同时满足：

- Route 推导出的 canonical target 等于解析后的 target；
- capability fold 包含请求 capability；
- Route 的每个 Link 对当前 Runtime Context 都满足明确的 applicability 条件。

每个 Link 的 applicability 必须由明确、可检查的 Runtime Context 条件决定，不能依赖 Provider 特例、隐式图搜索或隐藏状态。当前实现采用的最小规则见[当前实现快照](../current-architecture.md)，不在稳定设计中固化。

若真实路径需要前一步产生后一步的 actor、endpoint 或 condition，应在声明、编译或 Instance 层增加最小且显式的输入输出契约，而不是放宽 identity、引用或 candidate 规则。

Provider executable 是否实际存在、Probe 是否成功、Observation 是否新鲜，都不参与静态有效性或 candidate selection。

## Candidate cardinality

匹配后应用唯一结果规则：

- 0 candidate：`unresolved`；
- 1 candidate：`resolved`，返回唯一 Route；
- 多 candidate：`ambiguous`，返回全部 candidates。

Candidates 只按 canonical Route ID 稳定排序。Evidence、cost、priority、偏好、声明顺序、Provider 类型、hop 数和最近成功时间不得隐式参与排名或选择。未来若需要选择策略，必须建立显式契约，不能改变既有 cardinality 含义。

## Resolved result

Resolved result 组合而不复制各层事实，至少包含：

- 输入 target、Binding 解释、canonical target 与请求 capability；
- canonical Route ID、ordered canonical Link IDs 和推导的 capabilities；
- target Entity 的稳定声明事实；
- 每一步的 Provider 标识、结构化 native context、credential references 和 Link evidence；
- target Entity、Route 与 ordered Links 关联的 documentation references；
- 按[Observation 设计](Observation设计.md)聚合的 Route evidence。

Documentation references 按 canonical subject 与 normalized ref 去重并稳定排序，同时保留来源关系。Provider 原生上下文遵循[Provider 设计](Provider设计.md)，使用 executable 与参数数组而非 shell command string。结果不得展开 Secret，也不生成万能 Connection 对象。

## 只读边界

Resolve 可以读取声明、Runtime Context 和已有 Observation，调用 Provider `Validate` / native context rendering，并计算结果。Resolve 不调用 Safe Probe、不写 Observation、不启动外部进程、不建立 session，也不执行任何 Route action。

Target 无法解析、声明无效或 Provider 未注册属于输入/声明错误；没有匹配 Route 是 `unresolved`，多个匹配 Route 是 `ambiguous`；没有适用 Observation 时 evidence 为 `unknown`，不阻止声明匹配。

相关验证场景统一由[测试设计](测试设计.md)维护。
