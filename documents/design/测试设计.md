# locus-link 测试设计

## 简述

本文以可运行的 concrete environment cases 验证公共契约与设计不变量。测试重点不是证明抽象存在，而是证明陌生 Agent 能通过 CLI、WebUI 或 locus-link MCP 获得可解析、可复用的 situated operational knowledge，并把实际 action 交给合适的 native 或既有 MCP provider。

## 职责

本文负责：

- 定义跨 Scope、Resolve、Provider binding、Observation、documentation 和 Source provenance 的验收场景；
- 约束数据库与 Gitea 两个现实 E2E；
- 规定工作区隔离和可复现产物。

本文不负责固定测试框架、MCP SDK、SQLite schema 或外部服务部署。

## 通用验证基准

- 从 Project semantic Binding 开始，不要求调用者先知道 canonical ID；
- Declared View 只包含 active Scope 与显式 import DAG，Profile 不注入声明；
- Binding、canonical Entity、显式 Route、`requires/provides`、provider binding 和 Source provenance 可结构化查询；
- Resolve 前后 Observation 数量不变；Probe 只记录实际测量的 Link；
- Observation applicability 区分 declaration digest、vantage、provider binding、Probe kind/version 和 relevant context fingerprint；
- Profile 无关设置变化不使 Observation 失效；
- Secret 只使用 reference，不进入 Registry、结果、错误或 Observation；
- documentation 只能解析到 owning Scope `docs/`，可通过 MCP Resource 渐进读取；
- native 与 MCP provider 最终回答同一问题：“该 Link capability 由哪个 concrete mechanism 满足”；
- 不要求 locus-link Core 执行 SQL、部署、SSH session 或任意 MCP tool；
- 外部 native/MCP 行为由工作区内确定性 helper 模拟；
- Home、Catalog/cache、State DB 和测试状态全部定向到工作区；
- 测试结束保留 `temp/e2e-run/`。

若结果只返回未解析的 README/YAML，而没有 canonical identity、Binding、Route、capability、provider binding、evidence、documentation association 和 provenance，测试应失败。

## E2E A：数据库访问

### 前置

- Project Binding `production-db` 指向 Environment 中的 canonical database Entity；
- Entity 保存 host、port、engine、database 等稳定事实；
- 显式 Route 表达 SSH tunnel 等前置 Link 与数据库 Link；
- Link 通过 `provides/requires` 传递 local database endpoint capability，不要求相邻 `to/from` 相等；
- 数据库 Link 至少准备两种可替换 fixture：native `psql` binding 与既有 PostgreSQL MCP server/tool binding；
- credential/documentation 只保存 reference；
- helper 模拟 endpoint、Safe Probe 与 MCP tool transport，不连接真实生产数据库。

### Agent 查询

```text
访问 production-db，并执行 SQL
```

locus-link CLI/Web/MCP 必须能回答：

```text
canonical target + owning Scope
Project Binding explanation
current actor + vantage
explicit Route + ordered Links
requires/provides per step
native or MCP provider binding
credential/documentation refs
latest applicable evidence + Probe semantics
source + requested/resolved revision + content digest
```

### 验收

- native 与 MCP fixture 得到相同 target/Route/environment knowledge，只在 invocation binding 上不同；
- locus-link MCP `resolve/status` 映射 Core 结果，不产生第二套 Router/Registry；
- documentation 可按 `locus://docs/{id}` 渐进读取，不默认返回全部正文；
- mutable requested revision 能追溯到具体 resolved commit/hash 与 content digest；
- SQL execution 由 Agent 调用 native `psql` 或 PostgreSQL MCP tool，locus-link Core 不执行 SQL；
- 缺少 MCP server/tool binding 时显式诊断；
- SSH Safe Probe semantics 从 TCP connect 升级为 handshake 时，旧 success 不证明新语义。

数据库 Provider binding schema、MCP tool reference 格式和 Context fingerprint 字段仍为 **deferred / unresolved**；E2E fixture 先证明最小信息需求，再升级公共契约。

## E2E B：Gitea + FRP + Worker + Production

### 前置

- Project Bindings `source`、`ci-worker`、`production` 指向 concrete Entities；
- Environment/shared Scope 通过显式 imports 进入 Declared View，不依赖本机 Profile attachment；
- 显式 Route 表达：

```text
dev
→ Gitea
→ FRP / bastion
→ worker
→ production
```

- 各 Link 声明 Entity relation、capability `requires/provides`、documentation/credential refs 和 native/MCP provider binding；
- helper 模拟 Gitea、FRP、Worker 与部署机制，不访问真实服务。

### Agent 查询

一个对现场完全陌生的 Agent 必须能结构化回答：

```text
target 是谁
为什么当前 vantage 不能直接访问
已知 operational method 是什么
每一步需要/提供什么 capability
当前 actor/vantage 是否适用
evidence 与 docs/credential refs 是什么
最后应调用哪些 native 或 MCP provider
```

### 验收

- Route 可以满足 `previous.to != next.from`，但 capability fold 必须自洽；
- Gitea/FRP/worker/deploy 机制保持 provider-native，不被统一 workflow DSL 重写；
- Profile 只改变 actor/vantage/local availability，不增加 Gitea、Worker 或 Production 声明；
- `device-b` 等不同 vantage 不复用不适用 evidence；
- 仅返回原始 YAML/README、不提供解析后的 Route/capability/provenance 时失败；
- Agent + native/MCP provider 若能可靠完成，Plan/Instance/Execute runtime 继续冻结。

是否需要最小 step runtime output（例如 ephemeral endpoint）仍为 **deferred / unresolved**。只有该 E2E 明确失败且能定位缺失字段时，才重新打开窄设计。

## Source、发现与 authority 场景

必须覆盖：

- embedded only 与 managed association only 各自唯一选择；
- embedded + incompatible managed candidate 显式冲突；
- `--scope/--registry` 显式选择绕过 implicit competition；
- local → Git authority switch 后 canonical identity 不变；
- remote update 失败保留 last valid revision；
- requested `main` 每次解析为 immutable revision，并在结果/diagnostics 中返回 content digest；
- 同一 Scope 多 active Sources 不通过 precedence merge。

Home/Catalog 尚未实现前，这组场景是目标验收，不得写成当前实现事实。

## Agent Interface 场景

locus-link MCP 首阶段只验证：

```text
Tools:     locus.resolve / locus.probe / locus.status
Resources: context / entities / links / routes / docs
```

- MCP tool 与 CLI/Web 对同一输入返回等价 Core 语义；
- `locus.probe` 是唯一有 Observation 写副作用的首期 MCP tool；
- Core package 不依赖 MCP SDK/protocol types。

具体 tool/resource schema 在实现前另行加入公共契约；当前为目标设计，不属于 v0 实现。

## Fixture 与运行目录

- 可审阅声明和模拟设备状态：`test/e2e/case/`；
- 运行时物化目录：`temp/e2e-run/`；
- helper executable：`temp/e2e-run/bin/`；
- Observation Store：通过 `LOCUS_STATE_PATH` 定向到 `temp/e2e-run/`；
- 完整复现入口：`test/reproduce.ps1`。

当前自动 E2E 使用真实 `locus`/`locus web` 子进程和确定性 helper；浏览器 QA 不让测试依赖工作区外安装。新增 MCP fixture 同样必须使用工作区内 helper，不连接用户 MCP Gateway 或凭据。

## 维护规则

- 新样例必须对应真实 operational path 或关键不变量；
- 字段级变化优先扩展现有数据库/Gitea样例；
- deferred 项不能以 placeholder schema 进入契约；
- 产品、CLI、Web 或未来 MCP 契约变化时同步 fixture、断言和当前实现快照。
